# Manual-only Shizuku and the native-owned CPU pair (plan, 2026-11-23)

Level: **M/L** — UI behavior, the authored/emitted profile surface, and the merge/transport
path. Plan first, then code, per `AGENTS.md`.

Two arguable product decisions, both of which turn out to be the same shape: an app-side
heuristic sitting on top of a fact the runtime already owns.

## Decision 1 — Shizuku is manual-only

### 1a. Remove every automatic path

The W3 dialog (`maybeSuggestShizukuForW3`, `GhostlockViewModel.kt`) fires when the last run's
stuck step starts with `w3`. That step is left `in_progress` when a W3 *route write* misses on
the final attempt, or when the process panics / is killed mid-W3. It is **not** left
`in_progress` when every W3 write routed but the `finit_module` verify failed — the pure
"seccomp clear failed" case leaves all three steps `completed`. So the dialog fires on route
misses and crashes and misses the stage failure it names.

Its only action, `toggleShizuku(true)`, can also make the next run impossible: an enabled but
not-`READY` Shizuku makes `runExploit()` open the Shizuku setup and return. A suggestion must
not be able to do that.

Remove:

- `maybeSuggestShizukuForW3()`, its `initialize()` call, `w3HintChecked`;
- the three `w3_shizuku_hint_*` strings (EN + ZH);
- `dialog is AppDialog.Confirm -> toggleShizuku(true)` — the hint's only payload. The other
  `Confirm` (profile-exported) is caught earlier by `selectUri != null`, and the generic branch
  would silently enable Shizuku if a third `Confirm` is ever added;
- the profile-level auto-enable: `applyRecommendedShizuku()`, `recommendedShizukuApplied`, the
  repository seed, and the "this kernel recommends Shizuku" toast;
- the unused `KernelSnapshot.recommendShizuku` and the catalog's derived set;
- the advisory blob log in `GhostlockUserService` (the wire field stays 0, below).

Keep: the `run_interrupted` Notice (any stuck step, with export), the Run Settings switch, the
status card.

### 1b. Remove `recommend_shizuku` from the config schema

The key is not read by the native; the app's only use was the recommendation seed. All 83
bundled assets carry `0`/absent (68 explicit `0`, 4 templates `null`, 11 never had it).

Stop authoring/emitting/shipping:

- bundled assets: strip the line from the 68 profiles and the 4 templates;
- extractor: stop emitting in `report.rs` and both `options.rs` renders; drop the key from the
  superset key list; update the 5.15.189 fixture comparison;
- ship tool: it renders from the extractor, so `--refresh-all` drops it for store-backed
  assets; hand-finished assets get a manual strip; `--check` must read clean;
- docs/templates: `PROFILE_SCHEMA.md` / `_ZH.md`, `docs/kernel_profiles/templates/*`;
- app: `OptionSuperset.TopLevelKeys`, `BuiltinProfileCatalog`, the editor exclusions in
  `AndroidProfileConfigController`.

**Compatibility.** `ProfileResolver.validate()` refuses any top-level key outside
`KnownTopLevel` (`"unknown top-level key"`). Every external profile generated by the current
extractor carries `recommend_shizuku = 0`, so deleting the key outright would invalidate all of
them. The key therefore moves to a **deprecated, accepted-and-ignored** set now (out of the
documented/authored schema), and the tolerance is removed at the next profile-schema bump (v4)
with a migration that strips it.

**Wire.** `meta.recommend_shizuku` stays for this cut as a constant `0`:
`NativeProfile.kt`'s `vu()` already defaults an absent key to 0. It leaves the wire in the same
future revision as `recommended_cpus`.

## Decision 2 — the native owns the CPU pair

The app's pair (a UI choice written into the document as `execution.selected_cpus`) is read by
`apply_profile` and then **always** overwritten by `cpu_select::select_pair` when two CPUs pin.
The only surviving path is `<2` usable CPUs, where the pair was never verified anyway. The
Shizuku AIDL's CPU arguments are unused; the timer tool derives its own layout; the harness
hardcodes 4,5.

Evidence from the existing logs (`external/port/**/stream.log`): 568 carry both
`recommended_cpus` and `selected_cpus`; 556 are pre-`778a9ff5` (r10) and ran on the profile
pair because no picker existed; 12 are post-r10 (duchamp, `4/5 → 7/4`); zero runs used the
`<2` fallback. The frozen native-document golden is built with `CpuPair(0,1)`
(`NativeDocumentEquivalenceTest`), so the wire has never carried the picker's value.

Remove:

- **config**: `ProfileMerger.applySelectedCpus` and the `pair` parameter; `selected_cpus` from
  the two assets that carry it; the `GeneralPaths` entries and labels; `customCpuPairHint` and
  its test; the `customCpuPair` state path; the resolver's `recommended_cpus → selected_cpus`
  mapping; the stale `remove("selected_cpus")` in `renderResolved`;
- **UI/preflight**: the Run Settings spinner and `cpuPairSelected`; `CpuPairProbe`,
  `PreflightFailure.CPU_PAIR_UNAVAILABLE`, and the preflight branch;
- **API**: `pair` from the load/merge/native-document/preflight/run/timer calls;
  `buildCpuPairs`/`cpuPairs`/`cpuPairLabels`/`selectedCpuPair`/`selectCpuPair`/
  `restoreCpuPair`/the `cpu_pair` preference; the unused Shizuku AIDL CPU arguments.

**Wire**: inject `0/1` for `execution.recommended_cpus` in `buildNativeDocument`'s `value`
lambda (the same place `compat_carrier` is injected). The golden and digest stay
byte-identical.

Keep: the native picker and its verified-pin fallback, the compat helper's fallback, the pair
in the native log, and the run meta's effective pair (parsed, not a guess).

## Non-goals

- Removing `recommend_shizuku` or `recommended_cpus` from the **wire** — one future revision,
  together.
- Making the profile pair authoritative.
- A fast-vs-stable cluster policy — gated on a controlled diting A/B (4/5 vs 0/1, 10 fresh
  boots per arm), because the timings are tuned for the gold cluster.

## Gates

- App + profile-core suites; extractor `cargo test`.
- `NativeDocumentEquivalenceTest` and the profile digest unchanged (proves the `0/1`
  injection is byte-identical).
- `ship_golden_profiles.py --check` after the asset/ship edits.
- A v3 external document carrying `recommend_shizuku` still validates (deprecated-key test).
- Device (diting): the run's logged profile digest matches the pre-change digest; the native
  logs its effective pair; no Shizuku dialog after a W3-stuck state; the switch still works.

## Order

1. 1a (UI-only, independent).
2. 1b (schema surface + extractor/ship + deprecated-key tolerance).
3. 2 (wire constant, config removal, picker/preflight removal, API cleanup).
4. Host gates, then one diting smoke.

## Implementation status (2026-11-23)

Landed on `document` (uncommitted):

- **1a** — the W3 dialog, its three strings, the generic `Confirm → toggleShizuku` branch, the
  profile-level auto-enable (`applyRecommendedShizuku`, the repository seed, the hint toast), the
  snapshot field and the catalog's derived set are gone; the interrupted-run notice remains, and
  the manual switch is unchanged.
- **1b** — `recommend_shizuku` is out of the authored schema: 72 bundled assets, the four
  templates, both extractor renders, the superset key list, the docs. `ProfileResolver` keeps it
  as a deprecated, accepted-and-ignored key (`DeprecatedTopLevel`), so existing v3 external
  profiles still load; the wire keeps `meta.recommend_shizuku` as a constant 0.
- **2** — `selected_cpus` is gone from the merger, the assets, the editor, the UI, the preflight
  and the controller API; `CpuPair`, `CpuPairProbe` and `CpuPairHintTest` are deleted. The app's
  `buildNativeDocument` and `ProfileExporter` both inject the neutral `recommended_cpus = 0/1`.

Gates: app + profile-core suites, extractor `cargo test`, native build/lint/host suite,
`ship_golden_profiles.py --check` (61 bundled, 0 missing, 0 mismatched, 12 exempt),
`NativeDocumentEquivalenceTest` unchanged (the wire is byte-identical), APK 867. The diting
smoke is still pending.
